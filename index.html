React Compiler
+ Hooks

How React finally handles memoization for us - and the new React 19 hooks worth knowing.
Before the compiler
Two ways people wrote React
Approach 1 · Minimalist
"Don't write memo at all.
Only optimize if we hit a real performance problem."
Approach 2 · Defensive
"Wrap everything in memo / useMemo / useCallback,
just to be safe."
The problem
Both approaches are right - and both are wrong

Neither camp is being lazy or paranoid. Each one is optimising for a real cost - they just pay a different price.

Writing too little memo
Your code stays clean and readable. But somewhere a heavy component keeps re-rendering on every keystroke, and nobody notices until a user says "the search feels sluggish."

A bottleneck is the one slow spot that holds everything up - like one closed lane on a highway. You only find it after it hurts.
Writing memo everywhere
Now nothing is obviously slow - but every file is full of wrappers. Dependency arrays drift out of date and cause stale-value bugs.

And it isn't free: each check itself costs time and memory on every render. You can memo your way into being slower.
So React said: stop guessing. The compiler reads the real code and decides for you - correctly, in every component.
A common trap · why manual is hard
useCallback & useMemo alone do nothing

In React, when a component re-renders, all its children re-render too - unless a child is wrapped in memo. A stable function or value only helps if the child is memo'd to notice it.

parent.jsx
const onSelect = useCallback(fn, []); // stable function ✓ const rows = useMemo(() => build(), []); // stable value ✓ // but OrderRow is NOT wrapped in memo → // parent re-renders → child re-renders anyway ✗ <OrderRow onSelect={onSelect} rows={rows} />
You need both
useCallback / useMemo on the parent and memo on the child. Miss either → no benefit.
Easy to get wrong
Forget one, or a wrong dependency array, and you're back to re-rendering - silently.
Meet the React Compiler
So what is it?

A build tool from the React team that reads your components and rewrites them to be faster - automatically adding the memoization you'd otherwise write by hand.

It's a compiler
Like Babel or TypeScript - it runs when your code is built, transforming it before it ships.
It ships in React 19
Opt-in today via a Babel/build plugin. Turn it on, write plain code, get the speedups.
It's safe
If it can't be 100% sure a component is safe to optimize, it simply skips it - no breakage.
It's automatic
No new syntax to learn. Your components look exactly the same - just faster.
The compiler · in one idea
Re-render everything, then skip what's safe

React's default is simple and safe: when anything changes, run the component again and rebuild everything. That's easy to reason about, but it redoes work whose inputs never moved. The compiler's whole job is to find that work and skip it.

1 · It reads, it doesn't guess
It traces which value is built from which - so it knows exactly what each thing depends on. No hand-written dependency array to get wrong.
2 · It runs at build time
All the analysis happens on your machine or CI when the code is bundled. The browser only ever sees the finished, optimised output - zero runtime cost for the thinking.
3 · It rewrites your component
It emits the same component wrapped in cache checks: "inputs unchanged? reuse last value." Exactly what you'd write by hand - everywhere, without mistakes.
4 · You write plain code
No memo, no useMemo, no useCallback, no new syntax. Your component looks like a normal component - it just stops doing wasted work.

Your code becomes a real AST

AST = Abstract Syntax Tree. These are the actual node names Babel produces - the same tree ESLint and TypeScript walk.

source
const greeting = "Hi " + user.name;
How to read it
Each box is a node with a type. Nodes contain other nodes. The compiler can point at any single node and ask about it - that is the whole reason for doing this.
Why not just text?
With text you can only search characters. With a tree you can ask "what is the left operand of that + ?" and get an exact answer.
the Babel AST for that line
VariableDeclaration kind:"const" └─ VariableDeclarator ├─ id: Identifier name:"greeting" └─ init: BinaryExpression operator:"+" ├─ left: StringLiteral value:"Hi " └─ right: MemberExpression ├─ object: Identifier name:"user" └─ property: Identifier name:"name"

High-level Intermediate Representation

One chained line hides a lot of work. HIR splits it so every line does exactly one thing - and each step is explained below.

one line you wrote
const top = orders.filter(o => o.status === status).sort(byTotal).slice(0, 10);
$1 = LoadLocal ordersPick up the orders array and give it a temporary name.
$2 = Function @context[status]Create the filter callback. @context records that it borrows status from outside - this is what replaces your dependency array.
$3 = MethodCall $1.filter($2)Actually run filter on $1 using callback $2. Result is the filtered array.
$4 = LoadLocal byTotalPick up the sort comparator. It borrows nothing, so no @context.
$5 = MethodCall $3.sort($4)Sort the filtered array from $3. Note it feeds off $3, not off orders.
$6 = MethodCall $5.slice(0, 10)Take the first ten from the sorted array.
top = StoreLocal $6Give the final result the real name top.
Read the chain: $1 → $3 → $5 → $6 → top, and $2 depends on status. So top depends on orders and status - derived from the code, never typed by hand.

Static Single Assignment - one name, one value

The rule: a name is assigned exactly once. If your code sets the same variable twice, each gets its own tag. Then phi() picks the winner where the branches meet.

✗ Same name set twice
let label; if (isVip) { label = "VIP"; } else { label = "Guest"; } render(label); // which one?
✓ Unique tags + phi
if (isVip) { label#1 = "VIP"; } else { label#2 = "Guest"; } label#3 = phi(label#1, label#2); render(label#3); // clear ✓
phi means "pick the value from whichever branch actually ran" - like two hallways merging into one door. Now every value traces back to exactly one origin, even through if/else.

What kind of value is it?

The type decides how you compare it and whether it can change - the two things caching depends on.

object { }, [ ]
Compared by identity, not contents. Build a fresh one each render and it looks "different" even when identical - the #1 cause of wasted re-renders.
function () => ...
Same trap. A new function every render is a new identity, so a memo'd child sees a changed prop and re-renders anyway - exactly the useCallback problem.
primitive number, string
Compared by value - 5 === 5 is true. Cheap and predictable, never a source of trouble.
JSX element <Banner/>
React never mutates it after it's made. Always safe to cache - hand back the same element and React skips that child entirely.
Why this stage matters: objects and functions are where the waste lives. Knowing the type tells the compiler where the risk is - and where caching actually pays.

What happens to each value - is it risky?

"Risky" means the value could still change after we'd want to cache it. Cache too early and you hand back stale data.

Createsafe-ish
const a = []
A new value is born, still mutable. Fine for now - but we must watch what happens to it next before trusting it.
Mutaterisky
a.push(x)
A direct change. If we cached a before this line, the cache now points at changed data - it's wrong.
MutateTransitiverisky
b = a; b.push(x)
Changed through a nickname. It's still the same underlying value - so caching a is just as unsafe.
Capturewatch
fn = () => a
Stored inside a function. If a changes later, fn's behavior changes too - so fn can't be trusted yet.
Readsafe
log(a)
Only looking, never changing. Reads can't invalidate a cache, so they're always safe.
★ Freezelocked
<C data={a} />
Handed to React via JSX. From here it can never change - this is the green light to cache.
The rule: cache a value only after it's Frozen. Caching something that could still Mutate = a "lying cache" - worse than no cache at all.

Which values can actually change?

Reactive = traces back to a prop or state, so it can differ between renders. Stable = can never change. Only reactive values need a cache slot.

the component
import { formatPrice } from "./utils"; const TAX = 0.17; function Cart({ items }) { const [coupon, setCoupon] = useState(""); const subtotal = items.reduce(sum, 0); const total = subtotal * (1 + TAX); const label = formatPrice(total); return <Total text={label} />; }
REACTIVE - needs a cache slot
itemsa prop - the parent can pass a new one
couponstate - setCoupon can change it
subtotalbuilt from items → inherits it
totalbuilt from subtotal → inherits it
labelbuilt from total → inherits it
STABLE - skip it entirely
TAXa module constant, never changes
formatPricean import - same function forever
setCouponReact guarantees a stable setter
Reactivity spreads outward: touch a prop or state, and everything built from it becomes reactive too. Everything else is a constant the compiler never has to check.

Group them, then write the code

Values that always change together become one group, guarded by one check. Here is exactly what goes in - and what comes out.

YOU WRITE THIS
function Banner({ user }) { const greeting = "Hi " + user.firstName; return <Title text={greeting} />; }
THE COMPILER EMITS THIS
function Banner({ user }) { const $ = _c(2); // 2 cache slots let greeting; if ($[0] !== user) { greeting = "Hi " + user.firstName; $[0] = user; $[1] = greeting; } else { greeting = $[1]; // reuse ✓ } return <Title text={greeting} />; }
Same component, same behaviour - plus a tiny if. If user is unchanged, the string is never rebuilt. All that analysis existed just to write this check safely and automatically.
The one concept worth knowing · Scopes
Independent groups = independent updates

The real power: values that depend on different inputs go in separate groups. Changing one input only re-runs its own group - the other stays cached.

✗ Without compiler - all in one render
// every render, BOTH run: const filtered = orders .filter(o => o.name.includes(query)); const onSelect = (id) => { selectOrder(id, userId); }; // type in search → BOTH rebuild // even though onSelect // has nothing to do with query
✓ Compiler - two separate groups
// GROUP A - depends on query if ($[0] !== query) { filtered = orders.filter(...); $[1] = filtered; } // GROUP B - depends on userId if ($[2] !== userId) { onSelect = (id) => {...}; $[3] = onSelect; } // type in search → only A runs ✓ // onSelect stays cached → // table rows DON'T re-render
Because filtered depends on query and onSelect depends on userId, they never share a check. That independence is what kills the wasted re-renders.
"The output still compares - so what actually changed?"
Both check. Only one does extra work first

Imagine checking whether your shopping list changed since yesterday.

useMemo · rewrites the list before checking
Every single render, before it can compare anything, it has to:

1. Find its place in React's list of hooks
2. Write out a brand new list of the things to watch
3. Build a brand new function - even when it is about to throw it away and reuse the old answer
4. Compare the two lists
5. Store everything again for next time

Only step 4 is the actual check. Steps 1, 2, 3 and 5 happen whether or not anything changed.
Compiler · the list is already written down
if ($[0] !== query)

Look in one box. Compare. Done.

Nothing new is created. No new list, no new function, no hook bookkeeping.

When nothing changed, the work is almost literally nothing - one lookup and one comparison.
Why it adds up: one screen can hold hundreds of these, re-rendering many times as you interact. Every useMemo throws away two freshly-made objects every time - and the browser has to keep cleaning them up. The compiler never makes them in the first place.

Part 2 · React 19 Hooks
Six hooks that cut boilerplate
use()
Read a promise or context in one line.
useOptimistic()
Show the result instantly, undo it if it fails.
useTransition() ★
Mark work as not urgent - now works with async.
useActionState()
Form loading, error and result in one hook.
useFormStatus()
A button reads its own form's status.
useDeferredValue() ★
Keep old results on screen while new ones load.
Four are brand new. Two (★) existed in React 18 and got upgraded - those are the ones that change how the UI feels, and the ones we will demo.
Hook · use()
Read a promise - or a context - in one line

The important rule: the promise is created outside the render and passed in. Create it inside the component and you start a new fetch on every render.

✗ Before - four pieces of state
function Orders() { const [data, setData] = useState(); const [loading, setLoading] = useState(true); const [error, setError] = useState(); useEffect(() => { fetchOrders() .then(setData) .catch(setError) .finally(() => setLoading(false)); }, []); if (loading) return <Spinner />; if (error) return <Err />; return <List items={data} />; }
✓ After - use() + Suspense
// 1. promise made OUTSIDE render const ordersPromise = fetchOrders(); // (no await - just the promise) // 2. parent hands it down + wraps <ErrorBoundary fallback={<Err />}> <Suspense fallback={<Spinner />}> <Orders promise={ordersPromise} /> </Suspense> </ErrorBoundary> // 3. the component unwraps it function Orders({ promise }) { const orders = use(promise); return <List items={orders} />; }
Suspense = loading
While the promise is pending React shows the Suspense fallback. You write no loading state.
Error Boundary = failure
If it rejects, the nearest Error Boundary catches it. You write no error state.
Also reads context
use(ThemeContext) works too - and unlike useContext it may be called inside an if.
Hook · useOptimistic()
Show the result instantly - like a TikTok like ❤️

Tap the heart - it fills red immediately and the count jumps, before the server confirms. If the request fails, React quietly rolls it back. You never write undo code.

✗ Before - manual, and it feels laggy
const [liked, setLiked] = useState(false); const [count, setCount] = useState(likes); async function like() { await api.like(videoId); // wait... setLiked(true); // UI updates setCount(c => c + 1); // only AFTER } // heart fills only once server replies 🐌
✓ After - instant heart
const [optimisticLikes, addLike] = useOptimistic( likes, (current) => current + 1 ); async function like() { addLike(); // ❤️ instant! await api.like(videoId); // bg } // fails? React reverts the ❤️ for you
optimisticLikes shows the pretend count right away. The real number takes over when the server responds - or snaps back if it errors. That instant feedback is what makes apps feel fast.

Hook · useActionState()
Where do result, error & pending come from?

Your action function returns the new state (result or error). The hook gives you that state back, plus a pending flag while it runs. All wired together automatically.

The action function returns state
async function createOrder(prev, formData) { try { const order = await save(formData); return { order, error: null }; // ↑ this becomes `state` } catch (e) { return { order: null, error: e.message }; // ↑ error path, also `state` } }
The hook hands it all back
const [state, action, pending] = useActionState(createOrder, { order: null, error: null }); <form action={action}> {pending && "Saving..."} {state.error && Error(state.error)} {state.order && "Done! ✓"} </form>
state = whatever your action returned (success or error). pending = true while it's running. action = hand this to your <form>. No separate useState calls to wire up.
// web forms - good to know
Hook · useFormStatus()
The button reads the form's status itself

A submit button deep inside a form asks the parent form directly: "are you submitting?" No passing props down through every layer.

✗ Before - drill pending down
function Form() { const [pending, setPending] = useState(); return ( <form> <Fields /> <Toolbar pending={pending}> <SubmitBtn pending={pending} /> // pass through every layer 😩 </form> ); }
✓ After - button reads it directly
// from react-dom, not react! import { useFormStatus } from "react-dom"; function SubmitBtn() { const { pending, data } = useFormStatus(); return <button disabled={pending}> {pending ? "Saving..." : "Save"} </button>; }
pending = is the parent form submitting right now. data = the values being sent (show "Creating Blue Widget..."). Two rules: import from react-dom, and the component must sit inside the <form>.

Hook · useTransition() · enhanced in 19
What's special: it now handles async

Mark work as "not urgent" so urgent things (like typing) can cut in front. New in React 19: the work can now await the server, and isPending stays true the whole time.

React 19
startTransition(async () => { await deleteOrder(id); // isPending stays true // through the whole await });
Why it matters
The slow server call runs in the background. Type mid-transition → React interrupts it, handles the keystroke, resumes. The UI never freezes.
Free error handling
If the async work throws, React catches it → your Error Boundary shows. No try/catch needed.
React 18: sync only. React 19: async supported.
Before the demo · what the two sides actually run
Same heavy work. Different priority.

Both sides rebuild a big list on every keystroke. The only difference is who gets to go first.

✗ WITHOUT - both updates are urgent
function Search() { const [text, setText] = useState(""); const [list, setList] = useState([]); function onType(e) { const v = e.target.value; setText(v); setList(buildBigList(v)); // heavy } return ( <div> <input value={text} onChange={onType} /> <BigList rows={list} /> </div> ); } // React must finish BOTH before it can // paint the new letter -> input freezes
✓ WITH - the heavy half waits its turn
function Search() { const [text, setText] = useState(""); const [list, setList] = useState([]); const [isPending, startTransition] = useTransition(); function onType(e) { const v = e.target.value; setText(v); // urgent startTransition(() => { setList(buildBigList(v)); // can wait }); } return ( <div style={{ opacity: isPending ? 0.6 : 1 }}> <input value={text} onChange={onType} /> <BigList rows={list} /> </div> ); }
Nothing got faster - the list still takes just as long to build. React just stopped making the keystroke wait for it. And isPending lets you dim the stale list while it catches up.

Hook · useDeferredValue() · enhanced in 19
Show old results while new ones load

Typing in a search box that renders a huge list? Let the input stay instant while the heavy list catches up a beat later - React keeps the old results on screen instead of freezing.

✗ Before - list blocks typing
function Search({ query }) { // heavy list re-renders on // EVERY keystroke -> input lags return <HugeList query={query} />; }
✓ After - deferred value
function Search({ query }) { const deferred = useDeferredValue(query, ""); // ^ new in 19: // initial value -> skeleton on // first render, no freeze // input uses `query` (instant) // list uses `deferred` (lags) return <HugeList query={deferred} />; }
The input binds to query so typing is instant. The slow HugeList binds to deferred, which lags behind - so the old list stays visible while the new one renders in the background.
Before the demo · what the two sides actually run
Same list. One value lags on purpose.

Here the search text arrives as a prop from the parent - we don't own the setState. So we defer the value instead of the update.

✗ WITHOUT - list uses the live value
function Results({ query }) { // query changes on every keystroke, // so BigList rebuilds every keystroke return <BigList query={query} />; } // screen locks up while it renders, // and you see nothing until it's done
✓ WITH - list uses the deferred value
function Results({ query }) { const deferred = useDeferredValue(query); const isStale = query !== deferred; return ( <div style={{ opacity: isStale ? 0.6 : 1 }}> <BigList query={deferred} /> </div> ); } // old list stays on screen (dimmed) // while the new one renders behind
There's no isPending here - you get staleness by comparing query !== deferred yourself. That comparison is how you dim the old results while the new ones build.

useTransition vs useDeferredValue · which one?
One question decides it: do you own the setState?

They solve the same problem - keeping the UI responsive - and you should not use both for the same update. Pick based on whether the state update is yours to wrap.

useTransition
You own the setState
Wrapsthe update code
Needsaccess to the setState call
Gives youisPending for free
Use fortab switches, submits, deletes, navigation - actions you trigger
startTransition(() => setTab(id))
useDeferredValue
The value comes from above
Wrapsthe value itself
Needsnothing - just the value
Gives youno flag - compare v !== deferred
Use fora prop from a parent, a value from a library or context you don't control
const d = useDeferredValue(query)
Default to useTransition when you can reach the state update - it's less clunky and hands you isPending. Reach for useDeferredValue only when the value arrives from somewhere you don't control.
Straight from the source · Dan Abramov, React team
The official answer on the RFC
What he's saying
useDeferredValue is basically startTransition, but with an API shaped like a useDebouncedValue helper you'd write yourself.
When it wins
When the value comes "from above" and you have no control over the matching setState call. Then it's less clunky than startTransition.
The two pitfalls he flags
1. Child components must be memoized or you get no benefit at all.
2. Don't pass always-new values into it, or you can cause loops.
Worth noting: pitfall #1 is exactly what the React Compiler now handles for you - it memoizes the children automatically.
